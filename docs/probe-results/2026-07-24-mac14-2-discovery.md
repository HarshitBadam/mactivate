## Hypothesis verdicts (this session)
- H-TAP-PALM:   **supported (preliminary) across the full intensity range — the discriminating feature is the Z-impulse sign, not amplitude.** The decisive discovery of the Step 8 analysis: palm-rest taps produce a **positive Z-axis impulse** (signed residual integrated ±25 ms around the peak) while typing keystrokes and trackpad clicks produce a **negative** one (palm taps 19/20 positive; typing 15/170 across two runs; trackpad 1/12) — the palm rest and the keyboard/trackpad deck evidently flex the chassis in opposite directions at the SPU. A three-part rule — events ≥0.04 g detrended magnitude with 150 ms refractory, grouped at ≤1 s gaps, accept groups of size 1–3 whose **first** member has positive Z-impulse — scored on ~797 Hz data: comfort singles 19/20, light (touchscreen-soft) singles 25/25, doubles 22/25, triples 25/26, alternating 2/3 pattern 29/29 groups accepted, with **zero false accepts** across 58 s typing + 29 s trackpad + 30 s rest. Caveats: (1) gate the *first* group member only — ring-down from a prior tap flips later members' impulse sign ~45% of the time; (2) multi-tap count errors are amplitude misses of the 2nd/3rd tap (double→single) — needs an adaptive lower member threshold after the first tap; (3) very firm hits (0.27–0.55 g) break the impulse gate (26/66 positive) but pass a pure ≥0.25 g amplitude tier (28/28, 0 FP), and their ring-down spawns aftershock events needing peak-scaled suppression; (4) one false accept in the older 29 s **100 Hz** typing capture (post-pause keystroke pair) — the impulse estimate needs the high rate, and long-tail typing qualification plus product-level keyboard-event gating remain necessary. No ALS-only feature measured so far separates these from a real hover. Product implications, all measured: (a) require a minimum ambient baseline before arming the gesture; (b) gate out machine-motion/lid events using the IMU (the carry/lid/rotation portion of this trial would be vetoed for free); (c) the residual risk — a person or object shadowing a stationary machine — remains unquantified because this trial mixed carried and stationary segments; a stationary-machine lighting-FP take is the missing measurement. **Stationary-machine trial + bright-room hover reference (this session): the missing measurement is now made, and it refutes the gesture for v1 — the false-positive class is *stronger* than the positive class on every measured feature.** Positive reference (`hand_near_bright_10hz`, 60 s, baseline 258–272 lux, machine stationary): deliberate ~1 s hovers register as 23 dip episodes of median depth **−32.7%** (range −22.5..−73.5%) with dwell of only **0.10–0.20 s** (1–2 samples at the 10 Hz ceiling) and 0.1–0.2 s recovery — a natural-height hover barely shadows the sensor, unlike the earlier hold-and-cover's −90%, and its ~1 s duration does *not* appear as sustained low-lux dwell. FP trial (`lighting_fp_stationary`, 60 s, machine untouched, baseline 262–303 lux): excluding the one light toggle (−99.3%, 2.5 s dwell) and the operator's annotated accidental hover at 26.3 s (−76%, 0.3 s), the **11 walking/leaning shadow episodes measure depth −38.1..−90.7% (median −48.5%) with dwell 0.1–0.8 s** — deeper and longer-dwelling than the deliberate hovers, with the machine perfectly still so IMU gating cannot veto them. No rule exists in this data: any depth/slope/dwell threshold loose enough to catch the median hover accepts essentially all walking shadows, and a strict full-cover rule (≥75% drop, ≥1 s dwell) accepts zero hovers while still firing on the light toggle. Combined with the dim-light refutation (~1 lux floor) and the earlier dynamic-lighting false positives, ALS-based hand-near fails its viability criterion in the one environment that remained (lit + stationary): **H-HAND-NEAR is removed from the v1 product scope.** The ALS path itself (unprivileged `CurrentLux` poll, 10 Hz ceiling) remains a validated acquisition capability for possible future fusion work.

## Deviations from prior-art claims (record per methodology)
1. **ALS default `ReportInterval` observed as 197380, not 5428500** (Apple Wiki claim). Possibly a macOS 26 difference, or an existing client (auto-brightness/True Tone) already lowered it. The probe tool reads-and-restores whatever value it finds.
2. **`CurrentLux` as a live, unprivileged registry property** was not documented in any surveyed source. Hand-wave trials confirmed its update cadence tracks the ~5 Hz `ReportInterval` exactly — H-HAND-NEAR is achievable with no root and no privileged helper for the ALS path. The `ReportInterval` is also writable unprivileged; a 50000 µs override yielded a measured **10 Hz ceiling** (intervals quantize at ~100 ms — likely the sensor's integration-time floor).
3. The ALS driver class on this machine is **`AppleSPUVD6286`** (device-specific subclass), not the generic driver name — capability detection must match by usage page/usage, not class name.
4. **The SPU IMU does not require root here** — refutes olvvier/section9-lab/taigrr's universal `sudo` requirement (all on earlier macOS versions) in an interactive user session on macOS 26.2. Architecture assumption 1 in [Architecture Options](../architecture-options.md) is invalidated; see the Decision Log.
5. The wake-state properties (`SensorPropertyReportingState`, `SensorPropertyPowerState`) are **absent** from the registry until first set, so "restore" for them means resetting to 0, not restoring a read value.
6. Driver entries report `ReportInterval=0` at rest while their `AppleSPUHIDDevice` parents report 8000 — the interval that matters for wake is the one written to the **driver** entry.
